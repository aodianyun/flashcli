# FlashHub Bundle 下载可靠性

本文说明 FlashHub Bundle 下载器当前实现的行为、限制和后续工作。英文版本是权威
规格；本文与其保持同步。

## 范围

下载器获取 FlashHub 索引及选定的 Bundle 文件。本次改进文件完整性校验、重试、取消、
时间限制、临时文件处理、最终提交和进度统计。不改变其他下载器、Bundle 选择、模型
执行逻辑或 FlashHub 索引/API 契约。

## 已实现行为

### 校验与最终提交

- `File.Size > 0` 时，实际接收字节数必须完全相等。响应超过预期大小时立即失败；EOF
  时发现字节不足也会失败。
- `File.MD5` 非空时，会校验完整候选文件的 MD5。Size 和 MD5 都提供时，两项都必须通过。
- 只有所有可用校验项都通过，才复用已有缓存文件。Size 和 MD5 都缺失时仍保留原有缓存
  命中行为，但文件未经验证。
- 每次尝试都在目标目录创建唯一临时文件。候选文件通过校验、同步写入并关闭后，才重命名
  到正式路径。下载或替换失败时，已有目标文件保持不变。
- 每次尝试都从字节 0 开始，不复用已下载的部分数据。

### 重试、超时与取消

- 默认每个文件最多完整尝试三次，包含首次请求。
- 可重试情况包括网络连接/请求失败、响应体读取中断、HTTP 408、HTTP 429 和 HTTP 5xx。
  普通永久 4xx、无效 URL、完整性校验失败和本地文件错误不会重试。
- 退避有上限且可取消。默认基准为 250 毫秒，按指数增长，最多 2 秒。HTTP 429 会考虑
  `Retry-After`，但不会超过该上限。
- 对标准 HTTP transport，默认连接/TLS 限制为 10 秒，响应头限制为 30 秒；无进展限制为
  90 秒，单次尝试总时长为 2 小时。调用方更早的 context deadline 或取消优先。
- 设置连接与响应头限制前会克隆标准 HTTP transport。对于自定义 `RoundTripper`，代码可以
  限制可取消的响应头等待，但无法单独限制连接阶段；请求和单次尝试的超时依赖自定义
  transport 遵守 context 取消。

### 临时文件清理与并发

- `SyncBundle` 开始时、获取索引之前，会递归扫描 Bundle 目录。它只删除 basename 以
  `.flashhub-download-` 开头、修改时间比当前时间早 24 小时以上的普通文件。扫描包含嵌套 Bundle
  目录；若 Bundle 根目录或子目录是符号链接则不会跟随，也不会删除其他文件名、目录或旧
  `.incomplete` 文件。
- 当前进程从临时路径创建开始，持续跟踪到删除或最终重命名。清理会跳过该进程中仍登记为
  活跃的路径。并发或重复清理时已经不存在的文件视为清理完成。扫描或删除错误会记为
  警告，但 `SyncBundle` 会继续下载，避免单个无法删除的遗留文件阻断正常请求；后续调用
  可以再次尝试清理。
- 扫描及删除通过限定在 Bundle 根目录内的文件句柄执行，并在删除前复核文件身份和年龄。
  这可防止 symlink 或 `..` 路径替换将删除操作重定向到已打开 Bundle 根目录之外；根目录
  内的挂载点仍会被扫描。
- 24 小时的年龄限制可以降低误删其他进程临时文件的可能性，但它不是跨进程所有权锁。
  年龄和文件身份检查只是某一时刻的状态；其他进程可能在最后一次检查后、删除前恢复写入
  或替换文件。若活跃下载超过 24 小时未修改，也可能被清理。较旧版本的下载器不会参与
  当前进程的路径登记，因此无法绝对保证不存在所有跨进程竞争。
- 进程崩溃后遗留的临时文件会一直保留，直到后续 `SyncBundle` 调用发现其年龄超过阈值。
  清理不会在崩溃或断电的瞬间运行。
- 旧路径 `<dest>.incomplete` 不会自动续传或删除，仍可能留在磁盘并占用空间。
- 并发下载使用各自独立的临时文件。进程内按目标路径加锁，只保护正式目标复核和重命名；
  网络传输不会串行化，也没有跨进程锁。
- 每个正式提交的候选文件都通过了该调用方提供的校验项。若校验项缺失或不足，无法证明
  内容身份。并发调用仍可能重复传输。若并发调用对同一路径使用冲突元数据，最后成功提交
  的调用决定目标内容；不提供目录级或版本级事务。

### 进度与错误

- `SyncBundle` 在下载期间报告实时进度。它记录各次尝试达到的最高偏移，因此重试不会对
  同一逻辑字节重复累计。已知大小的文件在下载成功前保持未完成，成功后补齐到索引大小；
  未知大小文件不消耗已知聚合总量。
- `DownloadFile` 的 Go 函数签名不变，但 `onBytes` 只在校验并提交成功后按有限大小分段
  报告，不是实时读取回调。`SyncBundle` 使用单独的内部回调提供实时进度。
- 下载器错误会指出 Bundle 相对路径、失败类别或 HTTP 状态，并在适用时包含尝试次数；
  不会包含原始签名 URL、URL 用户信息、query 或 token。
- Go 公开方法签名、FlashHub 索引字段、下载 URL、最终目标路径及已完成缓存布局不变。

## 后续工作

目前未实现 HTTP Range 续传。后续工作可增加 `Range` 和 `Content-Range` 校验、正确处理
206 与 416 响应、ETag 和 `If-Range` 一致性检查、跨请求或进程重启复用部分文件，以及续传
进度统计。任何续传实现都必须保留本文所述的完整性校验、取消处理、有界重试和安全最终
提交。

## 验证

专项 Go 检查命令：

```bash
cd go
go test ./internal/flashhub -count=1 -v
go test -race ./internal/flashhub -count=1
```

测试使用本地 HTTP Server 和临时目录，不需要 FlashHub 凭据或模型文件。
